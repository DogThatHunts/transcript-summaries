Two Anthropic engineers demonstrate how to build production-grade prompts using a real-world Swedish insurance claim scenario to show the power of iterative design and structured context.

In this presentation, Hannah and Christian from Anthropic's Applied AI team demonstrate prompt engineering best practices using a real-world car insurance claims scenario. They guide the audience through the iterative process of refining a prompt—moving from a naive, context-poor query that hallucinates a skiing accident to a highly structured, system-prompt-backed query that accurately determines fault from a Swedish accident report and a hand-drawn sketch. Along the way, they share Anthropic's internal framework for structuring prompts, leveraging system prompts for caching, and using XML tags to guide Claude's reasoning.

Key insights

  • Prompt engineering is an empirical, iterative science. Getting the best results from an LLM requires starting with a simple prompt, identifying failure modes, and iteratively baking domain intuition and constraints into the instructions.
  • Structure prompts systematically for API use. For single-turn API calls, Anthropic recommends a structured layout: task description first, followed by dynamic content, detailed instructions, examples, and a final repetition of critical constraints.
  • Leverage system prompts for static context. Background information that never changes (such as the structure of a standard insurance form) should live in the system prompt. This is highly efficient and ideal for prompt caching to reduce latency and cost.
  • Use XML tags for clear boundaries. Claude is fine-tuned to recognize XML tags, making them highly effective delimiters for separating user preferences, document structures, and few-shot examples.
  • Enforce factual confidence. Instructing the model to stay factual and avoid guessing when uncertain prevents hallucinated claims, which is critical in high-stakes environments like insurance adjustment.

The anatomy of a structured prompt

Hannah outlines Anthropic's recommended structure for building robust prompts, particularly when deploying Claude via an API where you need the model to nail the task on the first attempt without back-and-forth conversation.

A great prompt should be organized into distinct components: 1. Task description: Define Claude's role and the objective up front. 2. Tone context: Specify how Claude should behave (e.g., remaining factual, confident, and refusing to guess if information is missing). 3. Dynamic content: Provide the input data, such as images, documents, or retrieved context. 4. Detailed instructions: Lay out a step-by-step guide on how Claude should reason through the task. 5. Examples (few-shot): Provide mock inputs and desired outputs to demonstrate edge cases. 6. Precise reminders: Repeat critical constraints at the very end to keep them top-of-mind for the model.

Iterative refinement: from skiing to car accidents

To demonstrate the necessity of context, Christian walks through three versions of a prompt analyzing a Swedish car accident report and a hand-drawn sketch.

  • Version 1 (The naive prompt): When given the images with a simple instruction to "review the accident report," Claude mistakenly guesses that the incident involves a skiing accident on a street called Chapmangatan. Because the prompt lacked context, the model made an incorrect assumption based on visual features.
  • Version 2 (Adding task and tone context): Christian refines the prompt by explicitly stating that Claude is assisting a human claims adjuster reviewing Swedish car accident forms. He also instructs Claude not to make an assessment unless it is fully confident. With this change, Claude correctly identifies the vehicular context but notes it lacks the confidence to determine fault.
  • Version 3 (Providing structural background): Christian and Hannah move the static details of the Swedish insurance form (explaining the 17 checkboxes, the two vehicle columns, and how humans might imperfectly fill it out) into the system prompt. With this complete context, Claude successfully and confidently determines that Vehicle B was at fault.

Maximizing performance with system prompts and caching

Hannah highlights that because the structure of the insurance form remains identical across every query, it is the perfect candidate for the system prompt and prompt caching.

By caching the static form structure, developers can significantly reduce API latency and cost. Claude no longer has to spend time deciphering the form's layout from scratch with every new image; instead, it immediately focuses on the dynamic handwritten markings and sketches provided in the user prompt.

The power of few-shot examples

For complex or ambiguous scenarios, Christian strongly recommends incorporating few-shot examples into the system prompt. By encoding visual examples (using Base64-encoded images) and pairing them with human-verified reasoning steps inside XML tags, developers can guide Claude through highly subjective "gray-area" decisions. This empirical tuning allows developers to push the limits of what the LLM can accurately automate.
