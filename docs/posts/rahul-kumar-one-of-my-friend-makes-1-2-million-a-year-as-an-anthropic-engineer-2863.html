The prompting playbook: best practices for LLM systems

Margot van Laar, an applied AI engineer at Anthropic, presents a comprehensive guide to prompting best practices through two practical scenarios: maintaining existing production prompts during model migrations, and building new agentic systems from the ground up.

General principles for prompt maintenance

Start with evaluations. Before making any changes, establish a rigorous evaluation suite to measure whether prompt modifications actually improve performance. Different models have different capabilities and behaviors, so degradation after migration can stem from either behavioral differences (fixable through prompting) or capability gaps (requiring a different model). A good eval suite should include three types of test cases: control cases that should always pass, edge cases where the model has previously failed, and cases that test the model's understanding of its own limitations.

Apply general hygiene first. Before targeting specific failure modes, clean up the prompt structure. Remove contradictory or outdated instructions, separate concerns using XML tags (role, guidelines, policy, tone), and eliminate redundant information. Van Laar notes that "if you're reading a prompt and you can't tell guidelines from policy from data, most likely the model isn't able to either." This foundational cleanup often produces immediate performance improvements.

Debugging production prompts: the customer support example

Van Laar walks through optimizing a customer support bot for a fictional telco company, Meridian Mobile, demonstrating how to systematically address three failing test cases.

The hotspot data problem. The model was deflecting customers to a URL rather than providing available information about hotspot allowances. The root cause: an overly defensive instruction ("never give a customer the wrong plan details") that was likely a patch for an earlier model's hallucination issues. As models improve at instruction following, such defensive patches become counterproductive. The fix was reframing the instruction to acknowledge that grandfathered customers have different allowances and that the customer's actual data is the source of truth. Key insight: Models can withhold information they have access to, not just invent false information.

The proration calculation failure. The model was giving vague answers about billing changes rather than exact calculations. The prompt told it to "always calculate prorated amounts correctly," but gave it no capability to do so. Key insight: Instructions don't add capability. The solution was introducing a tool—a calculate_proration function—that the model could call. This separated the reasoning task from the calculation task, allowing reliable outputs.

The billing error escalation problem. The model was trying to diagnose billing conflicts instead of escalating to a human. The original instruction stated the cost of escalation ($8) without mentioning the cost of getting it wrong (refunds, lost trust). The model optimized for minimizing escalation costs. The fix was presenting both sides of the trade-off. Key insight: As models become more capable, they need balanced information to make good trade-offs, not one-sided directives.

Building new systems from scratch: the scheduling agent

When building a new agentic use case, Van Laar compares multiple approaches to creating a weekly staff schedule that respects hard constraints (minimum headcount per shift, employee availability, etc.).

Model selection matters. Starting with Sonnet 4.6 and a simple prompt produced many constraint violations. Upgrading to Opus 4.7 significantly reduced violations (though still failing). Adding adaptive thinking to Opus made it reliably generate compliant schedules but tripled token usage and latency.

Prompt optimization has limits. Improving the prompt for Sonnet 4.6 (adding reasoning steps and a "check your work" instruction) helped but still failed on some cases due to output length limits. Increasing max tokens made the problem worse, not better.

The agentic approach wins. Rather than trying to solve everything in one prompt, Van Laar split the task into three separate prompts: a generator (create initial schedule), an evaluator (identify specific violations with evidence), and a repairer (fix violations). This generate-evaluate-repair loop achieved 100% compliance with fewer tokens and lower latency than the single-prompt approaches. An additional benefit: soft constraints (e.g., "avoid scheduling Harry with Sally") can be added at runtime in the evaluator prompt, without modifying the underlying evaluation logic.

Key takeaways

  1. Evaluations provide rigor. You can't improve what you don't measure. Build eval suites early and use them to validate every change.

  2. Structure matters. Use XML tags to separate concerns. Unclear prompts lead to unclear model behavior.

  3. Beware of defensive patches. Instructions added to fix one model's weaknesses often become liabilities with newer, more capable models. Use version control to track why defensive instructions exist so you can revisit them.

  4. Give capability, not just instructions. Telling a model to do something well doesn't make it capable of doing it. Use tools, structured outputs, or other mechanisms to enable the behavior you want.

  5. Split complex tasks. For agentic systems, breaking work into separate prompts (generate, evaluate, repair) often outperforms trying to do everything in one prompt.

  6. Balance trade-offs explicitly. Modern models are good at weighing competing priorities if you present both sides. One-sided directives lead to overfitting.
